Files, staging and commits

Git records changes you explicitly commit. Start with these concepts before trying a command.

📁
The Repository ("Repo")
Project Folder + Time Machine

A repository contains Git metadata and recorded commits. Your working folder can also contain edits and untracked files that Git has not recorded.

💾
The Commit
A Game Save Point

A commit records the staged snapshot and links to its parent history. Retained commits let you inspect earlier content; returning to it may affect your current files.

🛒
The Staging Area (git add)
Your Shopping Cart

git add copies the current contents of chosen files into the staging area. git commit records that staged snapshot. Later edits stay unstaged until you add them again.

☁️
Remote & Pipelines
Cloud Storage & Configured Robot

A remote is another repository, often hosted on GitHub, GitLab or Bitbucket. CI runs configured jobs when their trigger conditions match. It does not automatically deploy every project.

Inspect Status

🎓 Computer Science Deep Dive: The Real Git Data Model (DAG, SHA Hashes, and Refs) Expand Technical Theory

While real-world analogies (save points, breadcrumbs, bookmarks, camera lens) provide an intuitive daily mental model, under the hood Git is an elegant, mathematically rigorous Directed Acyclic Graph (DAG) built atop an immutable content-addressable object store. Here is the formal technical architecture:

1. Directed Acyclic Graph (DAG)

Git history is formally represented as a Directed Acyclic Graph $G = (V, E)$:

  • Vertices ($V$): Immutable commit objects representing project snapshots.
  • Directed Edges ($E$): Pointers directed backwards from child commits to their parent(s). A commit points to its parent because the parent existed first; the parent cannot know its future children.
  • Acyclic Invariant: It is mathematically impossible for a commit to be its own ancestor, preventing infinite loops during graph traversal.
  • Topological Ordering: History ordering depends on the chosen options in operations like git log and git rev-list.

2. Content-Addressable Object Store

All data in .git/objects/ is addressed by a cryptographic checksum (SHA-1 / SHA-256):

  • Blob: Raw file data (binary or text). Filenames and permissions are not stored inside blobs.
  • Tree: Directory structure mapping filenames, file modes (POSIX permissions), and blob/tree SHA hashes.
  • Commit: Top-level object storing: the root Tree hash, zero or more Parent commit hashes, author/committer timestamps, and the commit message.
  • Annotated Tag: A tag object naming a target object, with a tagger and message; a signature is optional. The tag reference itself can be moved.

3. References (Refs) & Symbolic Refs

Branches and HEAD are lightweight pointers, not folder copies:

  • Branch Ref: A 41-byte text file in .git/refs/heads/<branch-name> containing a single 40-character hexadecimal commit hash. When you commit, Git writes the commit object and updates this file.
  • HEAD (Symbolic Ref): The file .git/HEAD contains ref: refs/heads/main, delegating where the working tree is anchored. In detached HEAD state, .git/HEAD holds a raw commit hash instead of a branch path.
  • Remote-Tracking Refs: Read-only pointers in .git/refs/remotes/origin/ reflecting the last known commit on the remote server.

4. Best Common Ancestor (BCA) & 3-Way Merge

How Git calculates merges without manual guesswork:

  • Lowest Common Ancestor (LCA): When merging two branches ($B_1$ and $B_2$), Git traverses the DAG backwards to find their Best Common Ancestor commit $A$.
  • 3-Way Diff Matrix: Git computes $\Delta_1 = \text{diff}(A, B_1)$ and $\Delta_2 = \text{diff}(A, B_2)$. Clean changes to disjoint lines are automatically combined. Changes to identical lines trigger conflict markers.
  • Merge Commit: The resulting snapshot has two parent pointers: Parent 1 ($B_1$) and Parent 2 ($B_2$).

Start a Git repository

Start here
Effects: local-change · remote-publish
Goal: Track a project that is not already a repository.
Git does not record every file save. Initializing creates repository metadata; staging selects a snapshot, and committing records it. Review files and secrets before the first commit. Publishing is a separate task.
Before you start

Choose the intended project folder. Check that it is not already inside another repository. Choose an initial branch name and configure your Git author name/email; Git 2.28+ supports init -b.

Worked example — check prerequisites
git init -b <initial-branch>
git status
# Create or edit a file, then stage only that intended file:
git add -- <filename>
git diff --staged
git commit -m "Initial commit"
Check the result: git status should identify your chosen branch. git log -1 --stat should show the intended first commit and files. Unstaged or untracked files may still remain; a completely clean tree is not required for a successful selected-file commit.
If the result differs

If Git reports an existing repository, stop and inspect its top-level directory. If identity or hooks prevent the commit, inspect that specific error; do not reinitialize or bypass hooks.

Clone an existing project

Start here
Effects: local-change
Goal: Get a local checkout from a verified repository URL.
Cloning creates a local repository, downloads available history and checks out its default branch when one exists. The remote name is normally origin for a plain clone, but inspect the result rather than assuming later targets.
Before you start

Copy the clone URL from the intended host and confirm you have read access. Choose a new destination folder. You do not need an existing local Git repository.

Worked example — check prerequisites
git clone <repository-url> <new-folder>
cd <new-folder>
git status
git remote -v
git branch -a
Check the result: Check that the folder, configured remote URL and checked-out branch match the intended project. An empty remote can produce an unborn branch without a commit.
If the result differs

A private repository can look missing when the account lacks access. Verify URL/account before retrying; do not paste credentials into a URL or overwrite an existing destination.

Save your first commit

Start here
Effects: local-change
Goal: Choose the changes to record, then check the snapshot.
Saving a file changes your working tree. git add copies its current contents into the staging area (index). git commit records the staged snapshot. If you edit again after adding, those later edits are not included until you stage them.
Before you start

Use an existing repository on the intended branch, with a file you have edited. If this is a new project, start with the repository guide. Set your Git author identity if needed.

Worked example — check prerequisites
git status
git diff
git add -- <filename>
git diff --staged
git commit -m "Describe the change"
git log -1 --stat
git status
Check the result: Compare the staged diff before committing with git show --stat HEAD afterwards. Only the intended staged snapshot should be recorded. Other files or later edits can remain uncommitted. No push occurs.
If the result differs

If there is nothing staged, inspect status and stage the intended changes. If the snapshot is wrong before commit, unstage without discarding edits. If the commit fails, inspect the identity/editor/hook error before retrying.

Create and switch branches

Everyday Git
Effects: local-change
Goal: Give a line of work a name and understand what switching changes.
A branch is a movable reference to a commit, not an isolated copy of your files. Normal branches share one working directory. Uncommitted changes may carry across a switch or prevent it. A worktree provides a separate working directory.
Before you start

Inspect status and preserve wanted work before switching. Choose an unused branch name and the correct starting commit.

Worked example — check prerequisites
git status
git branch --show-current
git switch -c <new-branch>
# Edit and commit your intended changes here.
# Preserve remaining work before switching:
git switch <existing-branch>
Check the result: After creation, git branch --show-current should report the new name. After switching back, verify the expected branch and inspect status. Existing commits remain reachable through their refs.
If the result differs

If switching would overwrite changes, preserve those changes first. Do not add discard/force flags just to make a switch succeed.

Choose how to undo a change

Everyday Git
Effects: local-change · history-rewrite · data-loss-potential
Goal: Separate unstaging, discarding edits and undoing a commit.
Unstaging changes the index and preserves working files. Discarding overwrites selected working edits. Amend rewrites a commit. Revert records an inverse commit and can conflict. These are different goals; do not run all alternatives.
Before you start

Identify whether the change is unstaged, staged or committed. Inspect both diffs, commit ownership and any operation already in progress.

Worked example — check prerequisites
# Start by inspecting; choose an action in the linked help guides:
git status
git diff
git diff --staged
git log -n 5 --oneline
Check the result: Define the intended outcome first: edits kept but unstaged, selected edits discarded, or an inverse commit recorded. Verify the corresponding index, working file or commit afterwards.
If the result differs

If the state is uncertain or an operation is in progress, gather fresh status. Git cannot guarantee recovery of discarded unstaged edits.

Fetch, integrate and publish changes

Everyday Git
Effects: local-change · history-rewrite · remote-publish
Goal: Understand three different operations when working with a remote.
Fetch updates local remote-tracking information without integrating it into your current branch. Integration is a separate merge or rebase decision. Push publishes to a chosen remote ref. The local Git operations are shared across hosts.
Before you start

Inspect the actual remote and tracking branch. Preserve local work. Check the team’s integration policy and whether your commits are shared.

Worked example — check prerequisites
git status
git remote -v
git branch -vv
git fetch <remote>
git log --oneline --graph --decorate --all -n 20
# Choose integration only after inspecting the fetched history.
# Publish separately after testing and verifying the destination.
Check the result: Inspect the fetched tracking ref and graph. After deliberate integration, check the intended history/files and run project tests. Verify the destination separately after publishing.
If the result differs

A rejected push can mean divergence, permissions or policy. Identify the cause; never select force-push from a rejection alone.

Understand configured CI test jobs

Cloud & Remotes
Scope: Remote Cloud Effects: Config change if installed
When to use: Understanding how a host runs a configured test job when its event and branch conditions match. These test-only sketches need project-specific dependency setup.
GitHub Actions (.github/workflows/ci.yml) 
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Tests
        run: npm test
What happens: Without an explicit workflow file, cloud hosts act solely as code storage. Job creation depends on the provider configuration path and matching triggers. GitHub uses .github/workflows; GitLab and Bitbucket Cloud use their documented root files.
Verify result: Check the "Actions" (GitHub), "Pipelines" (GitLab), or "Pipelines" (Bitbucket) tab in your web browser to view live job logs.
Related: git push · .github/workflows · .gitlab-ci.yml · bitbucket-pipelines.yml

Temporarily set work aside

Everyday Git
Effects: local-change · data-loss-potential
Goal: Save local changes for later without confusing apply and drop.
stash push -u includes untracked files but excludes ignored files. Applying a stash may conflict and retains the stash entry. pop also attempts to remove it after successful application. Review the result before dropping an entry.
Before you start

Inspect tracked, staged, untracked and ignored work. Identify the original branch and intended stash. Preserve important work separately.

Worked example — check prerequisites
git status
git stash push -u -m "Work in progress"
# Inspect status before switching to an existing branch:
git switch <other-branch>
# Finish/preserve that work, then return:
git switch <original-branch>
git stash list
git stash apply <stash-reference>
Check the result: Inspect restored file contents, git diff and git diff --staged. The intended stash should still be listed after apply. Do not assume status is clean or the staged arrangement was recreated.
If the result differs

If application conflicts, inspect status and resolve deliberately. There is no generic stash-apply abort. Do not drop the stash until you have verified and preserved the result.

Resolve an identified merge conflict

Everyday Git
Effects: local-change · data-loss-potential
Goal: Decide the final file contents, stage them and finish the merge.
Conflict markers show competing content; deleting markers alone is not enough. Choose a correct final result, test it, then stage it. Modify/delete conflicts may have no text markers. Only continue after all unmerged paths are resolved.
Before you start

Read full git status to identify a merge. Rebase, cherry-pick and revert have their own continuation commands. Preserve wanted work and inspect every unmerged path.

Worked example — check prerequisites
git status
git diff --name-only --diff-filter=U
# Edit and test the intended final contents.
git add -- <resolved-file>
git status
# For an identified merge with all paths resolved:
git merge --continue
Worked example — check prerequisites
git status
git diff --name-only --diff-filter=U
Check the result: No unmerged paths should remain. Inspect the merge commit’s parents and tree, and test the intended combined changes. Re-paste fresh status if using guided checks.
If the result differs

For an identified merge, git merge --abort may cancel it; recovery of pre-existing uncommitted work is not guaranteed. Do not use merge continuation for a different operation.

Rewrite unshared commits with interactive rebase

Advanced Git
Effects: local-change · history-rewrite · data-loss-potential
Goal: Reorder or combine a selected private commit sequence.
Rebase replays changes onto a chosen base and may create new commit identities. Interactive actions can reorder, combine or remove commits. Replayed patches may conflict; linear history is a choice, not proof of correctness.
Before you start

Verify the selected commits have the needed ancestor and are unshared. Preserve work, inspect history and agree any collaboration policy before rewriting.

Worked example — check prerequisites
git status
git log --oneline -n 6
# Only if the inspected private sequence has this ancestor:
git rebase -i HEAD~3
# Resolve and stage conflicts before rebase --continue.
# If cancellation is intended, inspect rebase --abort guidance.
Check the result: Inspect the resulting graph, intended file tree and project tests. Confirm the selected changes remain present in the intended order; do not publish rewritten history automatically.
If the result differs

If rebase stops, read status and inspect the current patch. During rebase, ours/theirs refers to the replay context. Use the confirmed operation’s continue/abort procedure.

Understand detached HEAD and keep your commits

Advanced Git
Effects: local-change
Goal: Inspect a commit directly, or give wanted committed work a branch name.
Detached HEAD means HEAD points directly to a commit instead of through a branch. It is normal for inspecting history. A branch can retain a wanted commit; uncommitted edits need separate preservation.
Before you start

Inspect HEAD and any uncommitted changes. If you created commits while detached, verify their IDs before switching elsewhere.

Worked example — check prerequisites
git status
git log -1 --oneline
git branch --list
# Use an unused name and verified commit ID:
git branch <rescue-name> <verified-commit-id>
Check the result: git log -1 <rescue-name> should identify the intended commit. Inspect its files. Branch creation alone does not switch working files or save uncommitted edits.
If the result differs

If you already switched away, inspect reflog for a retained commit. Do not assume the branch name is main or switch until wanted work is preserved.

Use separate working folders with worktrees

Advanced Git
Effects: local-change
Goal: Check out separate branches without another full clone.
Worktrees share repository objects while having separate working directories and indexes. They are the appropriate comparison when you need parallel folders; normal branch switching does not create that isolation.
Before you start

Inspect current worktrees and branch use. Choose a new folder and an existing branch not already checked out elsewhere.

Worked example — check prerequisites
git worktree list
git worktree add <new-folder> <available-branch>
# Work in the new folder and preserve its changes.
git worktree list
# Remove only after confirming its work is no longer needed:
git worktree remove <new-folder>
Check the result: Check the registered path and checked-out branch in worktree list, then inspect status inside that folder. Before removal verify its work is committed/preserved.
If the result differs

If Git refuses because a branch is already checked out or a worktree has changes, investigate that state. Do not force removal as a generic fix.

Find a retained commit with reflog

Advanced Git
Effects: local-change
Goal: Locate committed work that lost a branch reference.
Reflog records local reference movements, not every file edit. It can help find a retained commit after a branch deletion or reset. It cannot guarantee recovery of discarded unstaged changes.
Before you start

This is committed-work recovery. Confirm the object still exists locally and choose an unused rescue branch name. Reflogs are local and may expire.

Worked example — check prerequisites
git reflog -n 20
git show <verified-commit-id>
git branch <unused-rescue-name> <verified-commit-id>
git log -1 <unused-rescue-name>
Check the result: Confirm the rescue branch points to the selected commit and inspect its tree for the wanted content. A new ref makes that retained commit reachable; it does not restore arbitrary disk edits.
If the result differs

If the commit is unavailable, stop rather than inventing a recovery guarantee. Look for backups or another clone where appropriate.

Find a regression with bisect; inspect attribution with blame

Advanced Git
Effects: local-change
Goal: Use distinct tools for a failing revision and line history.
Bisect narrows a regression by classifying revisions. blame shows last-change attribution for lines; it is not proof of who caused a bug. Reliable test classifications matter more than speed.
Before you start

Preserve work and choose a reproducible test with known good/bad revisions. Bisect checks out intermediate commits; older revisions may need different build dependencies.

Worked example — check prerequisites
git bisect start
git bisect bad <known-bad-commit>
git bisect good <known-good-commit>
# Test the selected revision, then choose exactly one:
# git bisect good
# git bisect bad
# git bisect skip
# Finish by returning to the original checkout:
git bisect reset
# A separate attribution example:
git blame -L 20,45 -- <filename>
Check the result: Inspect and reproduce the change identified by bisect; then verify the original checkout after reset. For blame, inspect the relevant commit and context rather than assigning fault.
If the result differs

If a revision cannot be tested, consider skip and report the resulting uncertainty. Incorrect good/bad labels can invalidate the search.

Create and publish a release tag

Working with a team
Effects: local-change · remote-publish
Goal: Name a verified commit and publish only the intended tag.
An annotated tag is an object with a message and a reference to a target. Creating it locally and publishing it are separate actions. Shared tag names should not be rewritten casually.
Before you start

Verify the commit, unused tag name, release policy and actual remote. Semantic versioning is a project convention, not something Git enforces.

Worked example — check prerequisites
git status
git log -1
git tag -a <new-tag> <verified-commit-id> -m "Describe the release"
git show <new-tag>
# Publish only after verifying the intended remote and policy:
git push <remote> refs/tags/<new-tag>
git tag --sort=version:refname -n 1
Check the result: Inspect the tag target and annotation. After authorized publication, verify the exact tag ref on the chosen remote. describe reports a nearby reachable tag, not proof of a release or successful publication.
If the result differs

If a tag already exists, inspect its target and publication status. Prefer a new reviewed name to force-replacing a shared tag.

Understand an explicit force-push lease

Advanced Git
Effects: history-rewrite · remote-publish · data-loss-potential
Goal: Review a coordinated history rewrite without treating it as routine sync.
An explicit lease checks whether the remote ref still equals the expected OID. That check does not prove ownership or that the replacement preserves wanted work. Shorthand leases can be affected by background fetches.
Before you start

Only consider this for a deliberately coordinated rewrite with verified ownership, target and expected remote OID. Preserve wanted history and understand who relies on the branch.

Worked example — check prerequisites
# Inspect first; no rewrite command is enabled here.
git status
git branch -vv
git remote -v
# Advanced syntax, after deliberate verification and coordination:
# git push --force-with-lease=refs/heads/<remote-branch>:<expected-oid> <remote> HEAD:refs/heads/<remote-branch>
Check the result: After any authorized publication, inspect the actual remote ref and intended history. If a lease fails, stop and investigate the new remote state rather than refreshing the expectation and overwriting it.
If the result differs

For a rejected ordinary push, start with diagnosis. A permission, policy or divergence error is not authorization to rewrite history.

Apply a selected commit with cherry-pick

Advanced Git
Effects: local-change
Goal: Bring a change onto another branch without merging all its history.
Cherry-pick applies a selected commit’s changes in the target context and usually records a new commit. The result can conflict or become empty; it does not transfer the whole source branch.
Before you start

Inspect the source commit and intended target branch, preserve work and start with no other operation in progress. Merge commits require additional mainline decisions not covered by this simple example.

Worked example — check prerequisites
git status
git show <ordinary-commit-id>
git switch <target-branch>
git cherry-pick <ordinary-commit-id>
# If conflicts occur, resolve/test/stage first.
# Only then: git cherry-pick --continue
# To cancel the identified operation: git cherry-pick --abort
Check the result: Inspect the resulting commit’s patch and target branch files, and run tests. A new identity may differ from the source; verify content rather than expecting identical hashes.
If the result differs

If the pick stops or becomes empty, inspect status and the intended outcome. Do not continue or skip automatically without understanding what is already applied.
