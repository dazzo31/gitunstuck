🎓 Computer Science Deep Dive: The Real Git Data Model (DAG, SHA Hashes, and Refs) Expand Technical Theory

While real-world analogies (save points, breadcrumbs, bookmarks, camera lens) provide an intuitive daily mental model, under the hood Git is an elegant, mathematically rigorous Directed Acyclic Graph (DAG) built atop an immutable content-addressable object store. Here is the formal technical architecture:

1. Directed Acyclic Graph (DAG)

Git history is formally represented as a Directed Acyclic Graph $G = (V, E)$:

  • Vertices ($V$): Immutable commit objects representing project snapshots.
  • Directed Edges ($E$): Pointers directed backwards from child commits to their parent(s). A commit points to its parent because the parent existed first; the parent cannot know its future children.
  • Acyclic Invariant: It is mathematically impossible for a commit to be its own ancestor, preventing infinite loops during graph traversal.
  • Topological Ordering: Git orders commits chronologically and topologically during operations like git log and git rev-list.

2. Content-Addressable Object Store

All data in .git/objects/ is addressed by a cryptographic checksum (SHA-1 / SHA-256):

  • Blob: Raw file data (binary or text). Filenames and permissions are not stored inside blobs.
  • Tree: Directory structure mapping filenames, file modes (POSIX permissions), and blob/tree SHA hashes.
  • Commit: Top-level object storing: the root Tree hash, zero or more Parent commit hashes, author/committer timestamps, and the commit message.
  • Annotated Tag: An immutable ref object pointing to a commit hash with GPG signature and tagger metadata.

3. References (Refs) & Symbolic Refs

Branches and HEAD are lightweight pointers, not folder copies:

  • Branch Ref: A 41-byte text file in .git/refs/heads/<branch-name> containing a single 40-character hexadecimal commit hash. When you commit, Git writes the commit object and updates this file.
  • HEAD (Symbolic Ref): The file .git/HEAD contains ref: refs/heads/main, delegating where the working tree is anchored. In detached HEAD state, .git/HEAD holds a raw commit hash instead of a branch path.
  • Remote-Tracking Refs: Read-only pointers in .git/refs/remotes/origin/ reflecting the last known commit on the remote server.

4. Best Common Ancestor (BCA) & 3-Way Merge

How Git calculates merges without manual guesswork:

  • Lowest Common Ancestor (LCA): When merging two branches ($B_1$ and $B_2$), Git traverses the DAG backwards to find their Best Common Ancestor commit $A$.
  • 3-Way Diff Matrix: Git computes $\Delta_1 = \text{diff}(A, B_1)$ and $\Delta_2 = \text{diff}(A, B_2)$. Clean changes to disjoint lines are automatically combined. Changes to identical lines trigger conflict markers.
  • Merge Commit: The resulting snapshot has two parent pointers: Parent 1 ($B_1$) and Parent 2 ($B_2$).

Start a Repository from Scratch

Onboarding
Scope: Local → Remote Effects: Local change
When to use: You started a new project folder on your machine and want to begin tracking it with Git and connect it to GitHub.
Initialization Sequence 
# 1. Choose your new repository's initial branch (Git 2.28+):
git init -b <initial-branch>

# 2. Stage all initial files and make the first milestone
git add .
git commit -m "feat: initial project setup"

# 3. Link to your empty GitHub repository and push
git remote add <remote> <repository-url>
git push -u <remote> <initial-branch>
What happens: Initializes local history, snapshots staged files, and publishes to the selected remote/branch. Review staged files and secrets before committing or publishing.
Verify result: Run git remote -v and git status to confirm clean tree and upstream tracking.
Related: git clone · .gitignore

Undoing Mistakes Safely

Undo & Recovery
Scope: Working Tree & Index Effects: Local change; possible data loss
When to use: You made accidental edits or staged files too early and need to back out without losing unintended work.
Restore Commands 
# 1. Unstage a file (SAFE: keeps your local edits in file):
git restore --staged <filename>

# 2. Discard uncommitted edits (PERMANENT: overwrites file):
git restore <filename>

# 3. Undo a pushed commit safely with an inverse commit:
git revert <commit-id>
What happens: restore --staged restores the index from HEAD while preserving working files. Plain restore copies the index version into working files; staged content may differ from HEAD. Unstaging against HEAD requires an existing commit.
Verify result: Run git status to confirm file state.
Permanent Loss Warning: git restore <filename> permanently overwrites uncommitted working edits. Those unstaged edits are not saved anywhere in Git.
Inspect git diff and git diff --staged first. Preserve wanted edits outside Git before discarding. Revert can conflict: inspect status, resolve then git revert --continue, or cancel with git revert --abort. Merge commits need a deliberate mainline choice.
Related: git reset · git revert · git reflog
🔬 Deep Dive: The Three Trees & Reset Matrix CS Theory

Git does not just track files; it coordinates Three Trees of repository state:

  • HEAD: The commit snapshot checked out in your repository database.
  • Index / Staging (.git/index): A binary cache recording file paths, stat caches, and blob SHA hashes for the next commit.
  • Working Tree: The physical files and directories you edit directly on your operating system filesystem.

The git reset command alters how many of these three trees move:

Reset FlagHEADIndex (Cart)Working TreeRisk Level
git reset --softMovesUntouchedUntouchedHistory rewrite; inspect target and shared history
git reset --mixed (default)MovesResetsUntouchedHistory rewrite; staging changes
git reset --hardMovesResetsOverwritten🔴 Destructive

Takeaway: git restore --staged copies from HEAD into Index (leaving Working Tree alone), while git restore copies from Index into Working Tree.

Working with Remotes (GitHub, GitLab, Bitbucket)

Cloud & Remotes
Scope: Remote & Local Effects: Local change; inspect prerequisites
When to use: Sharing your commits with teammates on GitHub, GitLab, or Bitbucket, or downloading their latest updates before merging.
Fetch, Rebase & Remote URLs 
# 1. Download remote changes WITHOUT altering working files:
git fetch <remote>

# 2. Pull & integrate linearly into your branch:
git pull --rebase <remote> <upstream-branch>

# 3. Upload your commits to remote:

Stashing: Temporary Work Shelving

Daily Essential
Scope: Working Tree & Stash Effects: Local change; inspect prerequisites
When to use: You are halfway through coding when an urgent bugfix is requested. Shelve your uncommitted edits so your workspace is clean, then restore them later.
Stash Lifecycle 
# 1. Stash changes (use -u to include newly created files):
git stash push -u -m "WIP: navigation refactor"

# 2. Your workspace is now clean. Switch branches or patch...
git switch hotfix

# 3. Commit/preserve the hotfix work, then return to the original branch:
git switch <original-branch>

# 4. Inspect the intended stash and apply it (keeps the stash):
git stash list
git stash apply <stash-reference>
# Verify restored files before separately dropping that stash.
What happens: Saves modified and untracked files into the stash stack and reverts your working tree to HEAD.
Verify result: Run git stash list to inspect saved stashes.
Stash caveats: -u includes untracked files, but excludes ignored files. Stash is local and applying it can conflict. Identify the intended stash and original branch; inspect status before and after applying. There is no generic stash-apply abort; preserve wanted work before resolving conflicts.

Interactive Rebase (Commit Polish)

Advanced / Pro
Scope: Local History Effects: History rewrite
When to use: Squashing WIP micro-commits into clean milestones before opening a Pull Request for your team.
Rebase Session 
# Rebase the last 3 local commits:
git rebase -i HEAD~3

# In editor:
# pick   = keep commit
# squash = combine into previous commit & merge message
# fixup  = combine into previous commit & discard message

# After resolving and staging any conflicts, choose continuation:
# git rebase --continue
# Or request cancellation instead (inspect status afterwards):
# git rebase --abort
What happens: Reconstructs a linear commit sequence with updated parent hashes.
Verify result: Run git log --oneline -n 5 to inspect the newly squashed history.
Golden Rule: Never rebase commits that have already been pushed to a shared public branch. Rewriting shared history breaks teammates' local branches.
🔬 Deep Dive: The Rebase Cherry-Pick Pipeline CS Theory

Git cannot modify existing commits because commits in the DAG are cryptographically immutable. Under the hood, git rebase executes an automated patch pipeline:

  • 1. LCA Discovery: Git traverses backwards to identify the Lowest Common Ancestor ($A$) between your branch and target base ($B$).
  • 2. Patch Generation: Commits unique to your branch are serialized into temporary diff patches in .git/rebase-merge/.
  • 3. HEAD Pointer Reset: Git resets HEAD to the target base commit ($B$).
  • 4. Sequential Replay: Git applies each patch one-by-one (automated cherry-pick). Each applied patch creates a brand new commit object with a new parent hash, new committer timestamp, and a completely different SHA checksum.

Why shared branches break: Teammates' local DAGs still point to the old commit SHAs. Pushing rebased commits results in divergent histories and duplicate commits.

Reflog Recovery (Lost Work)

Advanced / Pro
Scope: Local Reflog Ledger Effects: Local change; inspect prerequisites
When to use: You accidentally ran git reset --hard, deleted a branch with unmerged work, or lost a commit and thought it was gone forever.
Reflog Rescue Recipe 
# 1. View chronological action ledger:
git reflog -n 15

# 2. Locate the commit hash before the mistake (e.g. HEAD@{2})
# 3. Create a rescue branch attached to that commit:
git branch rescue-branch <verified-commit-id>
What happens: Reflogs can locate retained local commits. Expiry and object pruning depend on configuration and maintenance; recovery is not guaranteed. Creating a branch makes a retained commit reachable again.
Verify result: Run git log -1 rescue-branch to confirm your lost code is restored.
Related: git reset · git branch
🔬 Deep Dive: Object Reachability & Garbage Collection CS Theory

Git almost never deletes your commits immediately. Even after git reset --hard or deleting a branch:

  • Unreachable Objects: The commit objects remain in .git/objects/. They are merely disconnected from named branch refs (dangling in the DAG).
  • Append-Only Reflogs: Files in .git/logs/HEAD and .git/logs/refs/heads/ log every SHA hash that references have pointed to locally.
  • Maintenance: Reflog expiry and object pruning use separate rules. Unreachable reflog entries normally expire sooner than reachable ones; configuration can change these defaults. Inspect retained commit IDs before creating a rescue ref.

Takeaway: Rescue retained committed work before pruning. Reflog cannot restore arbitrary discarded unstaged edits. Inspect git show <commit-id> before creating a rescue branch.

Regression Hunting (bisect & blame)

Advanced / Pro
Scope: Local History Effects: Local change (bisect checks out commits)
When to use: A bug appeared and you need to pinpoint the exact commit out of hundreds that introduced the regression, or see who authored specific lines.
Bisect Binary Search 
# 1. Start binary search:
git bisect start
git bisect bad                 # Current version is broken
git bisect good v1.2.0          # Known good previous release

# 2. Test intermediate commits checked out by Git:
git bisect good   # (or 'git bisect bad')

# 3. Finish and return to active branch:
git bisect reset

# Inspect line-by-line author timestamps:
git blame -L 20,45 src/app.js
What happens: Performs a binary search across commit history in logarithmic steps ($\log_2 N$), isolating the faulty commit in minutes.
Verify result: Git outputs: [hash] is the first bad commit with author and commit message.

Release Tags & Semantic Versioning

Release Engineering
Scope: Repository Checkpoints Effects: Local change; remote publish
When to use: Marking an official production release, milestone, or version number (e.g. v1.0.0) in your Git history.

git tag -a v1.0.0 -m "Release v1.0.0: Initial public launch"

# 2. Push tag to GitHub (tags are not pushed by default!):

Force-Push with an Explicit Lease

PR & Team Hygiene
Scope: Remote Tracking Branch Effects: Remote publish; history rewrite; possible loss
When to use: A coordinated update to an exclusively owned review branch after a deliberate rewrite. A lease does not establish ownership or guarantee that teammates' work is preserved.
Inspect and Coordinate Before Rewriting 
# Inspect repository and remote first:
git status
git branch -vv
git remote -v

# After coordination, use verified values and expected remote object ID:
# git push --force-with-lease=refs/heads/<remote-branch>:<expected-oid> <remote> HEAD:refs/heads/<remote-branch>
# Do not execute while any prerequisite remains unknown.
What happens: An explicit lease checks the remote reference against the expected object ID you deliberately verified. The shorthand lease depends on local tracking refs and may be weakened by background fetches. Even a matching lease can overwrite wanted history.
Verify result: Inspect the remote branch and intended history after publication. If rejected, stop and inspect new remote commits; do not simply refresh the lease and overwrite them.

Port Isolated Commits (cherry-pick)

Branch Maintenance
Scope: Commit Plucking Effects: Local change; inspect prerequisites
When to use: Applying a specific bugfix commit from one branch (e.g. main) into a separate maintenance or release branch without merging the whole branch.
Cherry-Pick Recipe 
# 1. Switch to target branch (e.g. maintenance branch):
git switch release/v1.0

# 2. Pluck specific bugfix commit by hash:
git cherry-pick 7a1b2c3

# If conflict occurs:
# git cherry-pick --continue
# Or cancel and return to safety:

What happens: Re-applies the exact code diff from the specified commit hash and records a brand new commit on the currently active branch.
Verify result: Run git log -1 --stat to confirm the bugfix commit was applied.
Related: git switch · git merge · git log --oneline
