The 60-Second Mental Model

If you have never touched a code repository or pipeline, here is how Git actually works in plain English.

📁
The Repository ("Repo")
Project Folder + Time Machine

A repository is your project folder paired with an automatic ledger. It tracks your files and records a permanent, rewound history of every saved change.

💾
The Commit
A Game Save Point

A commit is a permanent snapshot of your project at one moment. If something breaks tomorrow, you can safely reload your codebase back to this exact checkpoint.

🛒
The Staging Area (git add)
Your Shopping Cart

Before you buy items, you place them into a cart. git add picks which edited files enter the cart. git commit pays at the register to seal the checkpoint.

☁️
Remote & Pipelines
Cloud Storage & Configured Robot

GitHub is a cloud host for your repo. A Pipeline (like GitHub Actions) is a robot that runs automated tests and deploys, if your repository has a workflow file configured.

🛡️ The Safe Daily Workflow Routine

Avoid blindly staging everything. Follow this verified sequence to inspect what changed, stage only intended files, review your staged diff, commit, and push when ready.

1
Inspect Status
See which files were modified or untracked.
git status
2
Stage Intended Files
Add only the specific files you meant to touch.
git add src/app.js
3
Review Staged Diff
Verify line-by-line what will enter the commit.
git diff --staged
4
Seal Checkpoint
Record the snapshot with a meaningful note.
git commit -m "feat: login"
5
Push When Ready
Publish to your remote upstream.
git push

Precise Staging & Checkpoints

Daily Essential
In plain English: Don't blindly bundle all files. Stage only the files ready for this specific milestone and review before committing.
Status, Add & Diff 
# 1. Review status of your working files
git status

# 2. Stage specific intended files
git add path/to/file.js

# 3. Review the exact staged snapshot
git diff --staged

# 4. Commit with a concise message
git commit -m "feat: add user authentication"
Caution on git add .: This command stages all non-ignored changes in the current directory tree. It can easily sweep in unintended scratch files or sensitive temporary files. Prefer naming files or using git add -p to stage hunk-by-hunk.

Branches: Isolated Sandboxes

Branches
In plain English: Want to test an idea without breaking the working app? A branch is an isolated sandbox. If it fails, delete it. If it works, merge it back.
Branch Navigation 
# Create and jump into a new sandbox:
git switch -c feature/redesign

# Work safely, edit files, and commit:
git add src/redesign.css
git commit -m "style: apply new color palette"

# Return to your main production line:
git switch main
TaskModern Standard (Git 2.23+)Legacy Overloaded
Switch branch git switch <name> Clean git checkout <name>
Create & switch git switch -c <name> Clear git checkout -b <name>

Undoing Mistakes Safely

Undo & Recovery
In plain English: Distinguish between un-staging a file (keeping your local edits) and discarding changes (permanently deleting edits).
Restore Commands 
# 1. Unstage a file (keeps your working edits untouched):
git restore --staged <filename>

# 2. Discard uncommitted edits to a tracked file (PERMANENT):
git restore <filename>

# 3. Undo a pushed commit safely with an inverse commit:
git revert <commit-id>
Permanent Loss Warning: git restore <filename> permanently overwrites uncommitted working-tree edits with the last committed version. Those unstaged edits are not in Git's database and cannot be recovered!

Syncing with Remote Remotes (GitHub)

Cloud & Remotes
In plain English: Send your commits to the shared cloud repository, or download team updates without disrupting your local workspace.
Push, Fetch & Pull 
# Download remote changes WITHOUT modifying local files:
git fetch origin

# Download AND integrate into active branch (fetch + rebase):
git pull --rebase origin main

# Upload your new commits to remote:
git push origin <branch-name>

# First-time upstream tracking:
git push -u origin main
Fetch vs. Pull: git fetch is download-only and 100% safe to run anytime. git pull downloads and immediately merges or rebases into your active working directory.

Pipelines & Automated CI/CD

Cloud & Remotes
In plain English: Pushing code to GitHub can trigger automated robots that run tests and publish your site—if a workflow is configured.

Without an explicit workflow file (such as .github/workflows/deploy.yml for GitHub Actions), GitHub acts solely as code storage. Pushing code only triggers checks or deployments when a CI/CD configuration file exists.

Workflow Location 
# Workflows reside in your repository root:
.github/workflows/deploy.yml   # GitHub Actions
.gitlab-ci.yml                 # GitLab CI

Stashing: Temporary Work Shelving

Daily Essential
In plain English: Shelve messy, half-finished edits so your working folder is clean for an urgent bug fix, then pull your work back down later.
Stash Lifecycle 
# 1. Stash changes (use -u to include newly created files):
git stash push -u -m "WIP: navigation refactor"

# 2. Your workspace is now clean. Switch branches or patch...
git switch hotfix

# 3. Return and restore your shelved changes:
git stash pop
Untracked Files Caveat: By default, plain git stash only saves tracked modifications and ignores newly created untracked files. Always add -u (or --include-untracked) if you created new files.

Merge Conflict Resolution

Branches
In plain English: When two branches change the same lines, Git marks the spot with conflict markers and waits for you to pick the correct code.

Git injects clean conflict markers into the file without explanatory text:

File with Conflict Markers 
<<<<<<< HEAD
const apiEndpoint = "https://api.v2.internal";
=======
const apiEndpoint = "https://api.v3.production";
>>>>>>> feature/endpoint-upgrade
Resolution Procedure 
# 1. Edit the file: remove the 3 marker lines and keep the right code
# 2. Mark the conflict as resolved:
git add src/config.js

# 3. Finalize the merge:
git merge --continue   # Or 'git merge --abort' to cancel

Interactive Rebase (Commit Polish)

Advanced / Pro
In plain English: Clean up and squash micro-commits on your local branch before opening a Pull Request.
Rebase Session 
# Rebase the last 3 local commits:
git rebase -i HEAD~3

# In editor:
# pick   = keep commit
# squash = combine into previous commit & merge message
# fixup  = combine into previous commit & discard message

git rebase --continue
git rebase --abort   # Safe escape hatch
Golden Rule: Never rebase commits that have already been pushed to a shared public branch. Rebase rewrites commit hashes; doing so on shared branches breaks your teammates' histories.

Detached HEAD Recovery

Advanced / Pro
In plain English: Occurs when you inspect a specific commit hash rather than a branch pointer.
Diagnosis & Safe Exit 
# Check if detached:
git status  # Shows: "HEAD detached at a1b2c3d"

# Exit A: Discard experiments and return to safety:
git switch main

# Exit B: Preserve commits made while detached:
git switch -c recovery-branch

Git Worktrees (Parallel Folders)

Advanced / Pro
In plain English: Check out two different branches simultaneously into separate directories without re-cloning.
Worktree Management 
# Check out hotfix into a sibling folder:
git worktree add ../project-hotfix hotfix-branch

# List all active directories:
git worktree list

# Remove folder when finished:
git worktree remove ../project-hotfix
