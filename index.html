The 60-Second Mental Model

If you have never touched a code repository or pipeline, here is how Git actually works in plain English.

📁
The Repository ("Repo")
Project Folder + Time Machine

A repository is your project folder paired with an automatic ledger. It tracks your files and records a permanent, rewound history of every saved change.

💾
The Commit
A Game Save Point

A commit is a permanent snapshot of your project at one moment. If something breaks tomorrow, you can safely reload your codebase back to this exact checkpoint.

🛒
The Staging Area (git add)
Your Shopping Cart

Before you buy items, you place them into a cart. git add picks which edited files enter the cart. git commit pays at the register to seal the checkpoint.

☁️
Remote & Pipelines
Cloud Storage & Configured Robot

GitHub is a cloud host for your repo. A Pipeline is a robot that runs automated tests and deploys, if your repository has a workflow file configured.

Start a Repository from Scratch

Onboarding
Scope: Local → Remote Risk: Safe
When to use: You started a new project folder on your machine and want to begin tracking it with Git and connect it to GitHub.
Initialization Sequence 
# 1. Initialize local repository with default branch 'main'
git init -b main

# 2. Stage all initial files and make the first milestone
git add .
git commit -m "feat: initial project setup"

# 3. Link to your empty GitHub repository and push
git remote add origin https://github.com/username/repo.git
git push -u origin main
What happens: Creates a hidden .git database in your folder, snapshots your initial files, and links your local main branch to GitHub.
Verify result: Run git remote -v and git status to confirm clean tree and upstream tracking.
Related: git clone · .gitignore

Clone an Existing Project

Onboarding
Scope: Remote → Local Risk: Safe
When to use: You want to download a team repository or open-source project from GitHub onto your computer and start working.
Clone & Inspect 
# 1. Download complete repository history into a new folder:
git clone https://github.com/username/repo.git

# 2. Enter directory and inspect status:
cd repo
git status

# 3. List all local and remote branches:
git branch -a
What happens: Downloads the full historical object graph, sets up origin remote tracking branches, and checks out the default branch.
Verify result: Run git branch -vv to see the active checked-out branch.
Related: git switch · git fetch

Precise Staging & Checkpoints

Daily Essential
Scope: Working Tree → Index Risk: Safe
When to use: You edited several files and want to seal a clean milestone snapshot containing only the changes intended for this commit.
Status, Add & Diff 
# 1. Review status of modified files:
git status

# 2. Stage specific intended files:
git add src/app.js

# 3. Review the exact staged snapshot:
git diff --staged

# 4. Commit with a clear note:
git commit -m "feat: add user authentication"
What happens: Places file snapshots into the staging index, then seals them into an immutable cryptographic commit object.
Verify result: Run git status to confirm "nothing to commit, working tree clean" and git log -1 to inspect the new commit.
Caution on git add .: Stages all non-ignored files under the current folder. Prefer naming files or using git add -p to stage hunk-by-hunk.
Related: git diff · git restore --staged

Branches: Isolated Sandboxes

Branches
Scope: Local History Risk: Safe
When to use: Starting a new feature, bugfix, or experiment without risking the working production code on main.
Branch Navigation 
# 1. Create and switch to a new branch:
git switch -c feature/redesign

# 2. Work safely, edit files, and commit:
git add src/redesign.css
git commit -m "style: apply new color palette"

# 3. Return to main branch when ready:
git switch main
What happens: Creates a lightweight 41-byte pointer to your current commit and moves HEAD to track it.
Verify result: Run git branch --show-current to verify your active branch.

Undoing Mistakes Safely

Undo & Recovery
Scope: Working Tree & Index Risk: Destructive / Reversible
When to use: You made accidental edits or staged files too early and need to back out without losing unintended work.
Restore Commands 
# 1. Unstage a file (SAFE: keeps your local edits in file):
git restore --staged <filename>

# 2. Discard uncommitted edits (PERMANENT: overwrites file):
git restore <filename>

# 3. Undo a pushed commit safely with an inverse commit:
git revert <commit-id>
What happens: restore --staged removes files from index without touching files on disk. restore copies the committed version over disk.
Verify result: Run git status to confirm file state.
Permanent Loss Warning: git restore <filename> permanently overwrites uncommitted working edits. Those unstaged edits are not saved anywhere in Git.
Related: git reset · git revert

Working with Remotes & Team Sync

Cloud & Remotes
Scope: Remote & Local Risk: Reversible
When to use: Sharing your commits with teammates on GitHub/GitLab, or downloading their latest updates before merging.
Fetch, Rebase & Push 
# 1. Download remote changes WITHOUT altering working files:
git fetch origin

# 2. Pull & integrate linearly into your branch:
git pull --rebase origin main

# 3. Upload your commits to remote:
git push origin <branch-name>
What happens: fetch updates remote-tracking references (`origin/main`). pull --rebase replays your local commits on top of incoming work.
Verify result: Run git status to confirm your branch is up to date with origin/main.
Fetch vs. Pull: git fetch is download-only and 100% safe to inspect anytime without modifying local files.

Pipelines & Automated CI/CD

Cloud & Remotes
Scope: Remote Cloud Risk: Read-Only
When to use: Understanding how pushing code triggers cloud robots that test code, build assets, and deploy websites automatically.
Workflow File Convention 
# Workflow files reside in repository root:
.github/workflows/deploy.yml   # GitHub Actions
.gitlab-ci.yml                 # GitLab CI
What happens: Without an explicit workflow file, GitHub acts solely as code storage. Pushing only triggers automated jobs if a CI/CD workflow file is configured.

Stashing: Temporary Work Shelving

Daily Essential
Scope: Working Tree & Stash Risk: Reversible
When to use: You are halfway through coding when an urgent bugfix is requested. Shelve your uncommitted edits so your workspace is clean, then restore them later.
Stash Lifecycle 
# 1. Stash changes (use -u to include newly created files):
git stash push -u -m "WIP: navigation refactor"

# 2. Your workspace is now clean. Switch branches or patch...
git switch hotfix

# 3. Return to branch and pop your shelved work:
git stash pop
What happens: Saves modified and untracked files into the stash stack and reverts your working tree to HEAD.
Verify result: Run git stash list to inspect saved stashes.
Untracked Files Caveat: Default git stash ignores new untracked files. Always pass -u if you created new files.

Merge Conflict Resolution

Branches
Scope: Working Tree & History Risk: Reversible
When to use: Git halts a merge or rebase because two branches altered identical lines and requires you to pick the right code.
Realistic Conflict Markers 
<<<<<<< HEAD
const apiEndpoint = "https://api.v2.internal";
=======
const apiEndpoint = "https://api.v3.production";
>>>>>>> feature/endpoint-upgrade
Resolution Steps 
# 1. Edit file: delete the 3 marker lines and keep the right code
# 2. Mark conflict resolved:
git add src/config.js

# 3. Finalize merge (or abort if you need to rethink):
git merge --continue   # Or 'git merge --abort'
What happens: Staging the cleaned file signals Git that the conflict is resolved. Finalizing creates the merge commit.
Verify result: Run git status to confirm all merge conflicts are cleared.

Interactive Rebase (Commit Polish)

Advanced / Pro
Scope: Local History Risk: History Rewriting
When to use: Squashing WIP micro-commits into clean milestones before opening a Pull Request for your team.
Rebase Session 
# Rebase the last 3 local commits:
git rebase -i HEAD~3

# In editor:
# pick   = keep commit
# squash = combine into previous commit & merge message
# fixup  = combine into previous commit & discard message

git rebase --continue
git rebase --abort   # Safe escape hatch
What happens: Reconstructs a linear commit sequence with updated parent hashes.
Verify result: Run git log --oneline -n 5 to inspect the newly squashed history.
Golden Rule: Never rebase commits that have already been pushed to a shared public branch. Rewriting shared history breaks teammates' local branches.

Detached HEAD Recovery

Advanced / Pro
Scope: HEAD Pointer Risk: Reversible
When to use: You checked out a raw commit hash instead of a branch name, and need to safely save any test commits you made.
Diagnosis & Safe Exit 
# 1. Check if detached:
git status  # Shows: "HEAD detached at a1b2c3d"

# Exit A: Discard experiments and return to safety:
git switch main

# Exit B: Preserve commits made while detached:
git switch -c recovery-branch
What happens: Creating a branch attaches a named pointer to your current detached commit so garbage collection will not prune it.
Verify result: Run git branch --show-current to verify you are back on a named branch.

Git Worktrees (Parallel Folders)

Advanced / Pro
Scope: Working Trees & Branches Risk: Safe
When to use: Checking out two different branches simultaneously into separate directories on your computer without re-cloning.
Worktree Management 
# 1. Check out hotfix branch into sibling folder:
git worktree add ../project-hotfix hotfix-branch

# 2. List all active directory locations:
git worktree list

# 3. Clean up folder when finished:
git worktree remove ../project-hotfix
What happens: Links multiple working directories to the same underlying .git repository database.
Verify result: Run git worktree list to verify registered directory paths.
