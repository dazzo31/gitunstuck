How Git actually works: intuitive conceptual models before diving into commands.

Quick Concept: Repo = Time Machine • Commit = Save Point • Staging = Cart • 5-Step Safe Routine
The Repository ("Repo")
Project Folder + Time Machine

A repository stores Git objects and references alongside your working files. Only commits record a history snapshot; saving a file in an editor does not create a commit.

The Commit
A Game Save Point

A commit records the staged snapshot. It excludes unstaged, untracked and ignored work. Keep another copy of important work; undoing later changes can still overwrite files.

The Staging Area (git add)
Your Shopping Cart

Before you buy items, you place them into a cart. git add picks which edited files enter the cart. git commit pays at the register to save a commit.

Remote & Pipelines
Cloud Storage & Configured Robot

GitHub is a cloud host for your repo. A Pipeline is a robot that runs automated tests and deploys, if your repository has a workflow file configured.

Computer Science Deep Dive: The Real Git Data Model (DAG, SHA Hashes, and Refs) Expand Technical Theory

While real-world analogies (save points, breadcrumbs, bookmarks, camera lens) provide an intuitive daily mental model, under the hood Git is a Directed Acyclic Graph (DAG) built atop an immutable content-addressable object store. Here is the formal technical architecture:

1. Directed Acyclic Graph (DAG)

Git history is formally represented as a Directed Acyclic Graph G = (V, E):

  • Vertices (V): Immutable commit objects representing project snapshots.
  • Directed Edges (E): Pointers directed backwards from child commits to their parent(s). A commit points to its parent because the parent existed first; the parent cannot know its future children.
  • Acyclic Invariant: It is mathematically impossible for a commit to be its own ancestor, preventing infinite loops during graph traversal.
  • Topological Ordering: Git orders commits chronologically and topologically during operations like git log and git rev-list.

2. Content-Addressable Object Store

All data in .git/objects/ is addressed by a cryptographic checksum (SHA-1 / SHA-256):

  • Blob: Raw file data (binary or text). Filenames and permissions are not stored inside blobs.
  • Tree: Directory structure mapping filenames, file modes (POSIX permissions), and blob/tree SHA hashes.
  • Commit: Top-level object storing: the root Tree hash, zero or more Parent commit hashes, author/committer timestamps, and the commit message.
  • Annotated Tag: A tag object naming another object, with tagger metadata and an optional signature. The tag reference itself can be moved.

3. References (Refs) & Symbolic Refs

Branches and HEAD are lightweight pointers, not folder copies:

  • Branch Ref: A 41-byte text file in .git/refs/heads/<branch-name> containing a single 40-character hexadecimal commit hash. When you commit, Git writes the commit object and updates this file.
  • HEAD (Symbolic Ref): The file .git/HEAD contains ref: refs/heads/main, delegating where the working tree is anchored. In detached HEAD state, .git/HEAD holds a raw commit hash instead of a branch path.
  • Remote-Tracking Refs: Read-only pointers in .git/refs/remotes/origin/ reflecting the last known commit on the remote server.

4. Best Common Ancestor (BCA) & 3-Way Merge

How Git calculates merges without manual guesswork:

  • Lowest Common Ancestor (LCA): When merging two branches (B1 and B2), Git traverses the DAG backwards to find their Best Common Ancestor commit A.
  • 3-Way Diff Matrix: Git computes Δ1 = diff(A, B1) and Δ2 = diff(A, B2). Clean changes to disjoint lines are automatically combined. Changes to identical lines trigger conflict markers.
  • Merge Commit: The resulting snapshot has two parent pointers: Parent 1 (B1) and Parent 2 (B2).

🔬 Deep Dive: The Three Trees & Reset Matrix CS Theory

Git coordinates Three Trees of repository state:

  • HEAD: The commit snapshot checked out in your repository database.
  • Index / Staging (.git/index): A binary cache recording file paths, stat caches, and blob SHA hashes for the next commit.
  • Working Tree: The physical files and directories you edit directly on your operating system filesystem.

The git reset command alters how many of these three trees move:

Reset FlagHEADIndex (Cart)Working TreeRisk Level
git reset --softMovesUntouchedUntouchedIndex and files retained; branch moves
git reset --mixed (default)MovesResetsUntouchedIndex replaced; files retained
git reset --hardMovesResetsOverwritten🔴 Destructive

Takeaway: git restore --staged copies from HEAD into Index (leaving Working Tree alone), while git restore copies from Index into Working Tree.

Rebase unpublished commits

🔬 Deep Dive: The Rebase Cherry-Pick Pipeline CS Theory

Git cannot modify existing commits because commits in the DAG are cryptographically immutable. Under the hood, git rebase executes an automated patch pipeline:

  • 1. LCA Discovery: Git traverses backwards to identify the Lowest Common Ancestor (A) between your branch and target base (B).
  • 2. Patch Generation: Commits unique to your branch are serialized into temporary diff patches in .git/rebase-merge/.
  • 3. HEAD Pointer Reset: Git resets HEAD to the target base commit (B).
  • 4. Sequential Replay: Git applies each patch one-by-one (automated cherry-pick). Replayed commits usually have new identities because their parents or metadata change. Git can reuse unchanged commits in a no-op rebase.

Why shared branches break: Teammates' local DAGs still point to the old commit SHAs. Pushing rebased commits results in divergent histories and duplicate commits.
