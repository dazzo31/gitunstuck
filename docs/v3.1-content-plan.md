# GitUnstuck v3.1 — Content Additions Plan (for LLM review)

Historical proposal. Its architecture/status statements describe an earlier checkout. Current learning scope and evidence are in learning-implementation.md and learning-evidence.md.

> Status: **PROPOSAL — for review before implementation**

> Scope: enrich existing recipe cards with recovery knowledge gaps, with all

## 1. Context & rationale

GitUnstuck v3.0.0 (shipped 2026-11-02) added the Terraform-Unstuck safety model:
per-recipe "When to stop" gates, authoritative source citations, read-only
"Check first" checklists, and a self-check exercise — plus a Developer Hub mode.

A gap analysis informed by Dangit, Git! and the Geekdas stash guide
found **four high-value recovery techniques** GitUnstuck does not currently teach.
These resources informed topic discovery only. All citations in this plan and
the resulting content must point to official Git documentation on `git-scm.com`.
These are the only items proposed; everything else in those sources is already
covered (reflog, `--amend`, `revert`, `diff --staged`, cherry-pick, `reset --hard
origin/main`, etc.).

**Design principle:** GitUnstuck is a *curated recovery guide and developer
resource*. Include techniques that help developers recover work, understand Git,
and handle everyday workflows. For v3.1, focus on the additions proposed below
and wire each through the existing safety-gate, check-first, and source-citation
structure added in v3.0.

## 2. Proposed additions (exactly four techniques, mapped to two cards)

### A. Enrich `card-stash` (currently id `card-stash`, ~line 3284)

Three additions, all stash-recovery oriented:

1. **Recover a dropped/cleared stash** (highest value — a true "lost work" rescue)
   ```bash
   # Find unreachable commits left behind by the dropped stash:
   git fsck --no-reflog | grep "dangling commit"
   # Inspect a candidate:
   git show <commit-id>
   # Restore it as a stash:
   git stash apply <commit-id>
   ```
   Note for the copy: this only works until `git gc` prunes unreachable objects,
   so "act quickly". Must carry a "When to stop" nuance: do NOT `git stash clear`
   without first checking `git stash list`.

2. **Turn a stash into a branch** (rescue when a stash no longer applies cleanly)
   ```bash
   git stash branch rescue-wip stash@{0}
   ```
   Creates a branch at the stash's base commit, applies the stash, and drops it if
   it applied cleanly.

3. **`git pull --autostash`** (one-command stash → pull → pop)
   ```bash
   git pull --autostash
   ```
   Convenience for "pulling while I have local changes" — already partially
   hinted by the existing stash card scenario, but not explicitly given.

### B. Enrich `card-undo` (currently id `card-undo`, ~line 3002)

Two additions, both "undo" recovery oriented:

4. **Restore a file to an older commit**
   ```bash
   # Modern (Git 2.23+):
   git restore --source <commit-hash> -- path/to/file
   # Legacy:
   git checkout <commit-hash> -- path/to/file
   ```
   The current card only shows `git restore <file>` (restores to HEAD). This adds
   the "go back further" case. Use the existing modern/legacy syntax toggle pattern.

5. **`git commit --amend --no-edit`** (add a forgotten file without a message edit)
   ```bash
   git add <forgotten-file>
   git commit --amend --no-edit
   ```
   Must carry the "When to stop" gate already present on the card: never amend a
   commit already pushed to a shared branch.

> **Deliberately OUT of scope (skip):** partial/interactive stash
> (`stash push -- <files>`, `-p`, `--keep-index`, `apply --index`) — power-user
> features that don't answer a recovery moment; `git clean` (deferred — see §6).

## 3. Constraints (must respect, unchanged from v3.0)

- **Monolithic `index.html`** (~6,000 lines), zero build step, zero dependencies.
  All edits are HTML/CSS/JS-inline, no new files except this plan doc.
- **Humanizer prose rules** (already applied across the repo): no em-dashes as
  connectors, no "not X but Y", no "verified" inflation, no forced triads, plain
  verbs. New copy must read like a person; keep it neutral/instructional.
- **Safety model consistency:** every new destructive command needs a
  "When to stop" gate (§4.1), a "Check first" checklist entry (§4.2), and a
  source citation (§4.3). Do NOT add a command without these three.
- **No new dependencies.** No `node_modules`, no external JS/CSS.
- **Official Git citations only.** Every citation must link directly to the
  relevant command manual or Pro Git section on `git-scm.com` and support the
  behavior described. Third-party tutorials may inform topic discovery but
  must not appear as citations in the plan or resulting content.
- **Test suite:** `node tests/test-analyzer.js` must stay green (155 assertions).
- **Accessibility:** new interactive elements need `aria-label`/`title`; code
  blocks stay inside `<pre class="code-content"><code>…</code></pre>`.
